# 集計と明細の標準形（4 文）

関連レコードを集計して別アプリに反映する、いちばん多い形。**親（集計先）と明細（別アプリ）を 4 文で全置換します。**
迷ったらこの形から始めてください（実測で検証済みの形）。

```sql
-- @ksql dialect: 1
DECLARE @cust = '';

-- 親（集計先）。キーの項目は「値の重複を禁止する」にしておく
UPSERT INTO LAPP_集計 (顧客コード, 件数, 売上, 集計日時)
SELECT @cust AS 顧客コード, COUNT(*) AS 件数, SUM(金額) AS 売上, @NOW() AS 集計日時
  FROM LAPP_受注 WHERE 顧客コード = @cust
ON DUPLICATE (顧客コード);

-- 明細（別アプリ）を全置換
DELETE FROM LAPP_集計明細 WHERE 顧客コード = @cust;
INSERT INTO LAPP_集計明細 (顧客コード, 担当者, 件数, 金額)
SELECT @cust AS 顧客コード, 担当者, COUNT(*), SUM(金額) FROM LAPP_受注
 WHERE 顧客コード = @cust GROUP BY 担当者;
```

設定側は、`params` に `{ "name": "cust", "source": "formula", "formula": "顧客コード" }` を 1 つ（詳細画面のボタンなら、表示中のレコードの顧客コード）。

## 要点

- **親の `UPSERT … SELECT` は `GROUP BY` を使わず、`@cust AS キー` + 集計関数で書く。**
  こうすると**集計元が 0 件でも 1 行（0 埋め）が書かれる**ので、「最後の 1 件のキーを変えた・消した」ときの後始末に
  件数で分岐する必要がありません。`GROUP BY キー` で書くと 0 件のときに行が出ず、集計先が古い値のまま残ります。
- 明細は **`DELETE` → `INSERT … SELECT` の全置換**。同じキーで何度流しても結果は同じです。
  素の `INSERT` に対する注意 `KSQL1305` が 1 件出ますが、置き換えのためのものなので**保存の障害にはしません**。
  ただし **`DELETE` のあとで `INSERT` が失敗すると、明細が消えたまま残ります**。それが困るなら、下の「全体再計算」と同じ
  「0 の行を `UNION ALL` で足してから集計する」形にして、**消す文を無くします**。
- 並び順を付けるときは **`SUM(…) AS 別名` + `ORDER BY 別名`**（集計式そのものは `ORDER BY` に書けない）。
- 集計先の**詳細画面に関連レコード一覧を置く**と、テーブルと同じ見え方になります。
- 一時テーブル（`CREATE TEMP TABLE`）に貯めてから書く形も使えますが、この 4 文では要りません。
  元アプリを 2 回読みますが、件数の分岐・`SET @cnt`・`EXIT` が消えるぶん短く、読みやすい。


## 月や年をまるごと作り直す（全体再計算）

「その月の請求を、受注から全部作り直す」のように、**キーが 1 つに決まらない作り直し**はこの形です。
消す文も 0 にする文も無いので、途中で失敗しても**前の値のまま残ります**。

```sql
-- @ksql dialect: 1
DECLARE @m = '';

-- 0) 作り直してはいけないものを守る（確定済みの月など）
ASSERT (SELECT COUNT(*) FROM LAPP_請求確定 WHERE 請求月 = @m) = 0, 'この請求月は確定済みです。再計算できません';

-- 1) 集める。元を先に集計し、今の集計先を「0 の行」として足す
CREATE TEMP TABLE #raw AS
SELECT 顧客コード, MAX(顧客名) AS 顧客名, COUNT(*) AS 件数, SUM(金額) AS 金額
  FROM LAPP_受注 WHERE 請求対象月 = @m AND 請求対象 = '対象'
 GROUP BY 顧客コード
UNION ALL
SELECT 顧客コード, '' AS 顧客名, 0 AS 件数, 0 AS 金額
  FROM LAPP_請求 WHERE 請求月 = @m;

-- 2) まとめる（kintone には行かない）
CREATE TEMP TABLE #agg AS
SELECT 顧客コード, MAX(顧客名) AS 顧客名, SUM(件数) AS 件数, SUM(金額) AS 金額
  FROM #raw GROUP BY 顧客コード;

-- 3) 書き込む（元が無くなったキーは 0 の行だけが残るので 0 で更新される）
UPSERT INTO LAPP_請求 (請求キー, 顧客コード, 顧客名, 請求月, 件数, 金額, 集計日時)
SELECT CONCAT(顧客コード, '-', @m) AS 請求キー, 顧客コード, 顧客名, @m AS 請求月,
       件数, 金額, @NOW() AS 集計日時
  FROM #agg
ON DUPLICATE (請求キー);

-- 4) 0 のまま残った行（もう対象でない）を消す
DELETE FROM LAPP_請求 WHERE 請求月 = @m AND 件数 = 0;
```

設定側は、`params` に `{ "name": "m", "source": "input", "formula": "" }` と、`inputs` に請求月を聞く項目を 1 つ。

### 要点

- **元（受注）を先に `GROUP BY` してから `UNION ALL`** する。月ぜんぶが相手なので、明細のまま積むと
  一時テーブルが元の件数ぶんに膨らみます（上限は `limits` の章）。`GROUP BY` は **`UNION ALL` の前の枝にだけ**掛かります。
- 集計先から足す 0 の行は、**文字の項目を `''`** にする。こうすると `MAX()` が元の側の**今の値**を採ります。
- **先に `UPDATE … SET 件数 = 0` で埋める形は勧めません。** 書き込みが 2 倍になり、0 にしたあとで失敗すると
  0 のまま残り、レコードの**更新履歴にも余計な 0 更新**が付きます。
- 消すのは**集計のあと**。先に消すと、消したあとで失敗したときに行ごと無くなります。
- 「もう対象でない行」を `NOT IN (SELECT …)` で消すことは**できません**（`sql` の章）。0 の行を足して
  `件数 = 0` で消すのが、この形を使う理由の 1 つです。
- キーを `CONCAT` で作るときも、**`DELETE` の `WHERE` には関数を書かない**（`sql` の章）。
  1 件ぶんのボタンなら、計算式でキーを組んでパラメーターで渡します。

## イベントに置くときは 1 文にまとめられないか見る

上の 4 文は、集計先の行がまだ無い場合に備えた形です。**イベント起動に置くとき**は、親の行があると分かっているなら `UPSERT` と `APPLY` を 1 文にまとめてください。

```sql
UPDATE LAPP_集計 SET 件数 = …, 売上 = …, 集計日時 = NOW() WHERE 顧客コード = @cust
  APPLY 明細 (REMOVE ALL ROWS; APPEND (担当者, 明細件数, 明細金額) SELECT …);
```

イベントはロックを取らないので、2 文に分けると別の実行と前後したときに**親が新しい時点・明細が古い時点**になり得ます。1 文なら 1 レコードの書き込みなのでずれません。詳しくは `sql` の章の「イベント起動に置く SQL」。

## 明細を「別アプリ」にするか「テーブル」にするか

| | 明細を別アプリ（この節） | 明細をテーブル（`apply`） |
|---|---|---|
| 文の数 | 4 文 | 3 文（親の `UPSERT` + `UPDATE … APPLY`） |
| 見え方 | 関連レコード一覧 | テーブル（帳票にも出せる） |
| 親が複数 | **まとめて処理できる** | **親が 1 件に決まる条件が必須**（複数親は「グループごと」で分ける） |
| 迷ったら | **こちら**（制約が少ない） | テーブルで見せたい・帳票に出したいとき |

どちらも使えます。**この 4 文の形は後の版でも有効なので、既存の設定を書き換える必要はありません。**

## 変更前のレコードでも実行する

「集計先のキー（顧客コード）を付け替えた」ときは、**新しい集計先だけ直すと古い集計先が残ります**。
起動に `event_edit`（保存後・編集）があるアクションで **`prevRecord: true`** にすると、
**変更前のレコードでも同じ SQL を 1 回実行**するので、前の集計先も直ります（パラメーターは変更前の値で評価）。
