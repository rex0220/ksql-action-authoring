# SQL の規約（許す文・パラメーターの置ける場所）

エンジンは **kSQL（`@rex0220/kintone-sql-tools`）の Flow dialect 1**。SQL は**アクションごとに 1 本**。

- 1 行目に **`-- @ksql dialect: 1`**。
- **20 文まで**（`DECLARE` も 1 文と数える）、**1 本 20,000 字まで**。
- アプリは**論理アプリ名 `LAPP_<名前>`** で書く（共通設定の対応表。実アプリ ID を SQL に書かない）。
- 項目は**項目コード**（ラベルではない）。`$id` はレコード ID、`$revision` はリビジョン。

## 許す文 / 拒否する文

| 区分 | 文 |
|---|---|
| **許す** | `DECLARE`、`SET`、`CREATE TEMP TABLE`、`DROP TEMP TABLE`、`ASSERT`、`EXIT`、`INSERT … VALUES`、`INSERT … SELECT`、`UPDATE`、`DELETE`、`UPSERT` / `MERGE`、`REORDER`、および `apply` の形の `APPLY` |
| **拒否** | **トップレベルの `SELECT` / `WITH`**（結果の表示先がない）、`SHOW`、`DESCRIBE`、`EXPLAIN`、`VALIDATE ONLY`、`IMPORT`、CSV 系、**サブテーブルへの直接の DML**（`INSERT INTO アプリ$テーブル`）、`apply` の形以外の `APPLY` |

表に無い種類は**保存時に拒否**します（fail-closed）。`SELECT` は、許す文の中（`INSERT … SELECT`、`SET @x = (SELECT …)`、CTE、サブクエリ、一時テーブル）でだけ使えます。

**`DELETE` には `WHERE` が必須**です（全件削除を防ぐため）。`DELETE FROM LAPP_集計;` は「DELETE 文には WHERE 句が必須です」で**保存できません**。
集計アプリを作り直す形では `DELETE FROM LAPP_集計 WHERE $id > 0;` のように、全件に当たる条件を書きます。

## パラメーター（`DECLARE` の外部注入）

```sql
DECLARE @cust = '';          -- 既定値つきで宣言する
DECLARE @_selected = [];     -- 配列（「まとめて 1 回」「グループごと」の予約名）
```

- 注入するのは**その SQL が `DECLARE` している名前だけ**。設定の `params` / `inputs` と**過不足なく 1 対 1**（予約名は自動）。
  片方にしか無ければ**保存時エラー**です。
- 名前は `[A-Za-z_][A-Za-z0-9_]*`、64 字まで、**大文字小文字を無視して一意**。予約名（`_` 始まり）は設定に書けません。
- 値は**文字列として束縛**されます（文字列連結ではないので SQL インジェクションは起きない）。数値項目との比較は数値として効きます。
- **置ける場所**: `WHERE` / `HAVING` の比較右辺、`IN (@a, @b)`、`UPDATE` の `SET` 値、`ASSERT` のオペランド、`SELECT` の定数列、`KLIKE` の右辺。
  **`VALUES` の直接の要素には置けません** → `INSERT INTO … SELECT @x AS 列` の形で書く。
- 空の扱い: 必須の入力が空 = 実行前エラー。任意の入力が空 = **注入しない**（`DECLARE` の既定値が使われる）。計算式が空文字 = 空文字を注入。
- 型: 注入できるのは**文字列**（と予約名 `_selected` の**文字列の配列**）だけ。`null` / 真偽値 / `NaN` は実行前エラー。
  日付は `YYYY-MM-DD`、日時は ISO 8601（タイムゾーン付き）。

### 予約パラメーター

| 名前 | 値 | 使える種類 |
|---|---|---|
| `_app` | 自アプリ ID | すべて |
| `_user` | ログインユーザーのコード | すべて |
| `_record` | 処理対象のレコード ID | レコード / 一覧の「1 件ずつ」 |
| `_status` / `_prev_status` | 変更後 / 変更前のステータス | `event_status` のみ |
| `_selected` | 選んだレコードの `$id` の**配列** | 一覧の「まとめて 1 回」「グループごと」（`IN @_selected` でだけ使う） |
| `_group` | 分ける式の値 | 一覧の「グループごと」のみ |

## 相対日付

`RELATIVE_DATE` 注釈つきの `DECLARE` には、**許された日付関数のトークンだけ**を渡せます。
置ける場所は **`WHERE` の比較右辺と `BETWEEN` だけ**で、`SET` の値には使えません。
設定側は入力項目の `type: "relative_date"` と対にします。

## as-of 関数

`@NOW()` / `@TODAY()` は**起動 1 回につき 1 回だけ**決まり、一覧の全レコード・検証・実行で同じ値を使います。
基準のタイムゾーンは共通設定の `timezone`。`APPEND … SELECT` のソースでも使えます。

## ガードと「何度流しても同じ結果」

**形**（メッセージは `,`（コンマ）で続けます。**`MESSAGE` という語はありません**）:

```
ASSERT [WARN] <式> <比較演算子> <式> [, 'メッセージ'];
ASSERT [WARN] <式> BETWEEN <式> AND <式> [, 'メッセージ'];
EXIT SUCCESS IF <同じ形の条件>, 'メッセージ';
```

```sql
ASSERT (SELECT COUNT(*) FROM LAPP_受注 WHERE 顧客コード = @cust) > 0, '対象の受注がありません';
ASSERT @cust <> '', '顧客コードがありません';
EXIT SUCCESS IF (SELECT COUNT(*) FROM LAPP_受注 WHERE 処理状況 <> '済') = 0, '対象がありません';
```

- `ASSERT` のメッセージは**省けます**が、`EXIT SUCCESS IF` の**メッセージは必須**です（無いと `pParse`）。
- `WARN` を付けると、条件が不成立でも**警告として続行**します（止めたいときは付けない）。
- 条件に書けるもの: 数値・**文字列リテラル**（`''` も可）・パラメーター（`@cust`）・算術式・スカラーサブクエリ。
  **書けないもの**（どれも `pParse`）:
  - **フィールド参照**（`FROM` が無いため）。レコードの値を見るならスカラーサブクエリにする
  - **`AND` / `OR` の複合条件** → `ASSERT` を**複数の文に分ける**
  - **条件全体を括弧で包む**（`ASSERT (@cust <> '') , '…'`）。括弧は算術式と読まれ、中は数値だけです
  - 裸の値（`ASSERT 1`）
- キーが空のときに止めるだけなら、`ASSERT` ではなく**実行条件**（`execCond` ＋ `execNgMessage`）でも書けます。
  押す前に止まって理由も出せるので、こちらのほうが利用者には親切です（`formula` の章）。
- **`ASSERT` で守れるのは「書いた条件」だけです。** 打ち間違いや空のパラメーターは止まりません。
  入力の必須・実行条件・**書き込み上限**とそろえて考えます（`config` の「不備で大量に書き換えないための 4 段」）。
- **`ASSERT` のメッセージは画面に出ます**（この製品で文を画面に出す唯一の例外）。
  だから**メッセージに業務データの値を書かない**（「対象がありません」のような固定の文にする）。
- 何度流しても同じ結果になる形で書く（`patterns` の標準形がその形です）。強い順に
  **① 0 の行を `UNION ALL` で足して集計し `UPSERT`**（消す文も 0 にする文も無いので、途中で失敗しても壊れない）、
  **② `UPSERT … ON DUPLICATE`**、**③ `DELETE` → `INSERT … SELECT` の全置換**（消したあとで失敗すると空のまま残る）。

## イベント起動に置く SQL（必ず守る）

保存後・ステータス変更のイベントで動かすアクションは、**ロックを取りません**（仕様 §10.4）。イベントには押し直す人がいないので、止めると「やらなかったこと」が誰にも伝わらないまま、データだけが先に進むからです。kintone の関連レコード集計と同じ考え方です。

そのかわり、**イベントに置く SQL は差分を足し引きせず、関係する範囲を毎回まるごと計算し直して反映する**形で書いてください。関連レコード集計が、1 レコードの変更で関係するレコード全体を集計し直すのと同じです。こう書けば、同じレコードを何度保存しても、ほかのレコードと前後しても、最新の正しい結果に落ち着きます。

| 書き方 | 可否 |
|---|---|
| 0 の行を `UNION ALL` で足して集計し `UPSERT` | ◎ 消す文も 0 にする文も無いので、途中で失敗しても壊れない（`patterns` の「全体再計算」） |
| `UPSERT … SELECT … ON DUPLICATE (キー)` | ○ キーの行を計算し直して上書きする |
| `DELETE` → `INSERT … SELECT`（全置換） | ○ ただし消したあとで失敗すると空のまま残る |
| `REMOVE ALL ROWS` + `APPEND … SELECT`（テーブル） | ○ |
| 消さずに足すだけの `INSERT` / `INSERT … SELECT` | **×** 保存のたびに増える |
| `SET 売上 = 売上 + 1` のような自分自身の足し引き | **×** 差分の反映になる |

**親の値とテーブルは、できれば 1 文にまとめてください。** 親の行があると分かっているなら `UPSERT` と `APPLY` を分けずに書けます。

```sql
UPDATE LAPP_集計 SET 件数 = …, 売上 = … WHERE 顧客コード = @cust
  APPLY 明細 (REMOVE ALL ROWS; APPEND (担当者, 明細件数, 明細金額) SELECT …);
```

1 文なら 1 レコードの書き込みになるので、別の実行と前後しても**親と明細がずれません**。2 文に分けると、親が新しい時点・明細が古い時点、ということが起こり得ます（明細を別アプリに持つときは分けるしかないので、`patterns` の標準形で書きます）。

これらは `kact_check` と保存のツールが**警告**として見ます（保存は止まりません）。

| コード | 意味 |
|---|---|
| `wEventAppend` | イベントに置いたのに、消さずに足すだけの `INSERT` がある |
| `wEventDelta` | 同じ項目を足し引きする代入がある |
| `wEventTwoStep` | 同じアプリの親の値とテーブルを別の文で書いている |

ボタンと一覧の一括はこれまでどおりロックを取るので、この規則はイベントに置くときだけの話です。

## 注意（warning。保存は止まらない）

| コード | 意味 | どうするか |
|---|---|---|
| `KSQL1305` | 素の `INSERT` は再実行で重複し得る | 全置換（`DELETE` → `INSERT … SELECT`）では避けられない。利用者に伝えるだけ |
| `KSQL1307` | `APPLY` の親の `WHERE` が 1 件に決まると読めない | キーを「値の重複を禁止する」にする。できないなら、重複時は実行時に止まることを伝える |
| `wEventAppend` | イベントに置いたのに、消さずに足すだけの `INSERT` がある | `UPSERT` か「`DELETE` してから `INSERT`」に書き替える（上の章） |
| `wEventDelta` | 同じ項目を足し引きする代入がある（`売上 = 売上 + 1`） | 元のデータから毎回計算し直す形にする |
| `wEventTwoStep` | 同じアプリの親の値とテーブルを別の文で書いている | できれば 1 文（`UPDATE … SET … APPLY …`）にまとめる |

知らないコードが来ても**エラー扱いにしない**（エンジンが診断を増やすため）。`kact_check` の `findings` の `level` に従います。

## 書くときに間違えやすいところ

- **`ORDER BY` に集計式そのものは書けません。** `SUM(金額) AS 売上` と別名を付けて `ORDER BY 売上` と書く
  （集計式を直接書くと parse エラー `KSQL1202`）。
- `GROUP BY` でキーをまとめると、**集計元が 0 件のときに 1 行も出ません**（集計先が古い値のまま残る）。`patterns` の形にする。
- **`NOT IN` は、中身が値のリスト（`確定 NOT IN ('確定')`）や配列（`NOT IN @keys`）なら書けます。**
  kintone の `not in` にそのまま乗るので、書き込む文の `WHERE` でも使えます。ただし**空配列の `NOT IN` は全件**に当たります
  （「選択が空なら何もしない」は `IN @_selected` 側で書く）。書けないのは次の**サブクエリの形だけ**です。
- **`NOT IN (SELECT …)` は、書き込む文（`UPDATE` / `DELETE`）の `WHERE` に書けません。** 検査は通りますが、
  実行計画で `WHERE predicate cannot be represented by kintone REST (… reason=WHERE_RESIDUAL)` と出て止まります
  （一時テーブル相手でも `temp table references in DELETE are not supported yet`）。
  「もう対象でない行を消す」は、**0 の行を足して集計し、`件数 = 0` で消す**形にします（`patterns` の「全体再計算」）。
  読み取りの `SELECT`（`CREATE TEMP TABLE … AS SELECT` のソース）には書けますが、**JavaScript 側の判定**になり、
  その取得が `EXACT` から `PREFILTERED` に落ちます（相手のアプリをもう 1 回読む）。
- **`WHERE` に関数を書くと実行時に落ちます**（`DmlConvertError`）。`DELETE … WHERE 請求キー = CONCAT(@cust, '-', @m)` は不可で、
  キーは**計算式で組んでパラメーターで渡します**（`WHERE 請求キー = @key`）。**`SELECT` の列に書く `CONCAT()` は問題ありません。**
- **`FROM (SELECT … UNION ALL …)` の入れ子（導出表）は書けません。** `UNION ALL` は `CREATE TEMP TABLE` に受けます。
- **`GROUP BY` は `UNION ALL` の前の枝にだけ掛かります。** 枝ごとに集計したいときは、それぞれの枝に書きます。
- 別アプリは**自アプリと同じ領域**（通常領域どうし・同じゲストスペースどうし）だけ。
- **選択肢とステータスには「既定の名称」を書きます。** `kact_fields` が返す `options` が既定の名称です
  （`lang` を付けずに取っているため）。kintone の「**言語ごとの名称**」で選択肢やステータスに
  言語ごとの表示名を設定している項目でも、**SQL は変えません**。プラグインが実行時に利用者の言語へ
  読み替えます（エンジン 3.91.0 の `optionNames: "canonical"`）。
  **表示名のほうを書くとエラーにならず 0 件**になるので、`kact_fields` に出ている値をそのまま使ってください。

## 実行計画（`kact_explain`）

書いた SQL が**どう動くか**は、取り込む前に `kact_explain` で見られます（文ごとに 種類・読むアプリ・kintone に投げる条件・
使う項目・API の見積もり）。`kact_check` が見るのは**形と規則**なので、次のような「規則としては正しいが意図と違う」ものは計画で気づきます。

- `WHERE` が kintone の条件にならず**全件取得**になっている（`kintone query: (全件取得)`）
- 書き込む文の `WHERE` に kintone へ渡せない条件が残っていて**止まる**（`reason=WHERE_RESIDUAL`。`NOT IN (SELECT …)` など）
- 読む件数の見積もりが大きい（`estimated API consumption` の `read`）
- 文の順番が思っていたのと違う（集計してから更新のつもりが、更新してから集計になっている）

**書き込む SQL は、アクションごとに見てください。** 1 本だけ見て通ったつもりになると、もう 1 本の同じ誤り
（`WHERE` の関数など）を見落とします。

**kintone には行きません**（`kact_fields` で控えた項目定義だけを使い、レコードは読みません）。控えの無いアプリがあると
その番号を知らせるので、`kact_fields` で取ってからもう一度見てください。
